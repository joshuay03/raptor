Raptor

Raptor is a high-performance, preloading, pre-forking, multi-threaded Ruby 4+ web server implementing Rack 3.2+, using NIO for non-blocking I/O and Ractors for parallel HTTP/1.1 and HTTP/2 parsing via native C extensions, which also implement HPACK compression.

[!NOTE] Your application does not need to be Ractor-safe. Ractors handle protocol-level work only; your Rack application is invoked on a thread pool, so any thread-safe Rack app (including Rails) works as-is.

Reference documentation is published at https://joshuay03.github.io/raptor.

Installation

Install the gem and add to the application's Gemfile by executing:

bundle add raptor

If bundler is not being used to manage dependencies, install the gem by executing:

gem install raptor

Configuration

Raptor reads options from a Ruby config file, environment variables, and command line flags, in increasing order of precedence. Run bundle exec raptor --help for the full flag list.

The config file evaluates to a hash of options. By default Raptor loads raptor.rb then config/raptor.rb from the working directory. Pass -c PATH to point at a specific file.

# raptor.rb

# Every key below is set to its default value; only include the ones you want to override.
{
  binds: ["tcp://0.0.0.0:9292"],
  socket_backlog: 1024,
  drain_accept_queue: false,
  workers: 4, # `Etc.nprocessors`
  threads: 3,
  max_threads: Float::INFINITY, # set to `threads` for a fixed pool
  cpu_affinity: false,
  clean_thread_locals: true,
  clean_fiber_locals: false,
  chdir: nil,
  environment: nil, # falls back to `RAILS_ENV`, then `RACK_ENV`, then `"development"`
  connection: {
    first_data_timeout: 30,
    chunk_data_timeout: 10,
    write_timeout: 5,
    max_body_size: nil,
    body_spool_threshold: 1024 * 1024,
  },
  http1: {
    ractors: nil,
    persistent_data_timeout: 65,
    max_keepalive_requests: 1000,
  },
  http2: {
    ractors: nil,
    max_concurrent_streams: 100,
    keepalive_interval: 10,
    keepalive_timeout: 5,
  },
  worker_boot_timeout: 60,
  worker_timeout: 60,
  worker_drain_timeout: 25,
  worker_shutdown_timeout: 30,
  refork_after: 1000, # `nil` on non-Linux
  before_fork: [],
  before_worker_boot: [],
  before_worker_shutdown: [],
  before_refork: [],
  plugins: [],
  stats_file: "tmp/raptor.json",
  control_url: nil,
  pid_file: nil,
  stdout_file: nil,
  stderr_file: nil,
  access_log_file: nil,
}

RAPTOR_WORKERS, RAPTOR_THREADS, and RAPTOR_MAX_THREADS set the corresponding options without a config file.

By default each worker adds threads beyond threads only while queued requests are waiting on blocking work such as database or network calls. It stops adding them once Ruby execution becomes the bottleneck, and the extra threads retire when the queue is idle. Set max_threads to cap this growth, or set it to threads for a fixed pool.

Plugins

Plugins start in the master process and can register lifecycle hooks that run in workers. Use them for metrics exporters, probes, or other integrations. Enable them in your config with plugins: [:stats_logger].

Raptor loads each name from raptor/plugin/<name> on Ruby's load path. A gem can provide that file, or you can require an application-local plugin before returning the config hash.

# lib/raptor/plugin/stats_logger.rb
require "raptor/plugin"

Raptor::Plugin.create(:stats_logger) do
  def start(cluster)
    in_background do
      loop do
        Raptor::Log.info(JSON.generate(cluster.stats_hash))
        sleep 10
      end
    end
  end
end

For an existing class, inherit from Raptor::Plugin and register it with Raptor::Plugin.register(:stats_logger, MyStatsLogger) instead.

start(cluster) runs once before the initial workers fork. cluster.options exposes configuration, including plugin-specific keys. Append callbacks to its before_fork, before_worker_boot, before_worker_shutdown, and before_refork arrays during startup. If your plugin opens a listener, close the worker's inherited copy with cluster.options[:before_worker_boot] << proc { @listener.close } so only the master serves it.

cluster.stats returns per-worker snapshots. cluster.stats_hash returns the same aggregate structure as GET /stats, including boot status, busy threads, capacity, backlog, and request counts. Both remain available while workers drain.

Override stop to close listeners and flush exporters. Raptor calls it after workers exit, in reverse plugin order, then stops and joins threads created with in_background. These callbacks also run before hot restart and when startup fails, so stop must handle partially initialized resources. Worker replacement and phased restart keep the same master plugin instances running.

Bindings

binds accepts any combination of these URIs.

  • tcp://host:port for TCP. localhost binds both IPv4 and IPv6 loopback addresses.
  • unix:///path/to/socket for a Unix domain socket.
  • ssl://host:port?cert=/path/to.crt&key=/path/to.key for TLS, negotiating HTTP/1.1 or HTTP/2 via ALPN.
  • h2c://host:port for cleartext HTTP/2.

Signals

Send to the master process.

Signal Effect
INT Graceful shutdown
TERM Graceful shutdown
HUP Reopen stdout_file, stderr_file, and access_log_file
USR1 Phased restart (rolling worker replacement)
USR2 Hot restart (restart master, keeping listening sockets)

A phased restart replaces workers one at a time while the master keeps running, picking up application code changes. A hot restart starts a new master with the original command line and the same listening sockets, picking up changes to configuration, dependencies, or Raptor itself.

systemd

Raptor supports socket activation and sd_notify, so it works with Type=notify units. When the socket unit is active, Raptor serves the listening sockets systemd passes in place of binds. Raptor sends READY=1 after all workers have finished booting, including their before_worker_boot hooks.

# /etc/systemd/system/myapp.socket
[Socket]
ListenStream=0.0.0.0:9292

[Install]
WantedBy=sockets.target

# /etc/systemd/system/myapp.service
[Service]
Type=notify
WorkingDirectory=/srv/myapp
ExecStart=/usr/bin/bundle exec raptor
ExecReload=/bin/kill -USR2 $MAINPID
KillMode=mixed

Stats

Workers publish their stats to stats_file, which defaults to tmp/raptor.json.

> bundle exec raptor stats
Master PID: 91348
Worker 0 (phase 0): pid=91350, requests=1234, busy=2/3, backlog=0, booted, last_checkin=10:42:01
Worker 1 (phase 0): pid=91351, requests=1199, busy=1/3, backlog=0, booted, last_checkin=10:42:01
...

Set control_url to a Unix socket URL such as unix:///tmp/raptor-control.sock to serve the same stats over GET /stats.

(Micro) Benchmarks

Raptor 0.24.0 vs Puma 8.0.2 vs Falcon 0.57.0. Each case has 3 fresh-process samples, interleaved in seeded shuffled rounds. Each sample warms up for 3s and measures for 15s. Metrics are independent medians. ± is (max − min) / 2 / median, not a confidence interval. Failure counts below each table sum all samples, so a failed run cannot disappear in a median. Throughput counts successful ordinary requests only.

Comparison columns show each server's change from Raptor's median for the baseline mode. Higher req/s is better. Lower p95 is better. Falcon's measurements are repeated against each Raptor mode, not rerun.

IO interleaves 5–10 sleeps of 0.5–1.5ms with small JSON renders. CPU interleaves 3–5 larger JSON renders with 25–50µs sleeps. Both discard the rendered JSON and return a short response. 64 KiB body sends a prebuilt response to isolate response transfer. SSE (native) uses Raptor's detached body versus blocking Enumerators. Raptor (enum) uses the same blocking body as Puma and Falcon, reusing their existing samples for comparison. The 20 streams are cluster-wide connections, not guaranteed to be evenly placed. Streams without complete headers after 2s remain connected and are counted as stalled.

Fixed (3), Scaling (3–16), and the IO-only Fixed (16) control separate tight concurrency, pool growth, and a prestarted larger pool. Falcon uses unbounded fibers and runs once per workload/protocol. Raptor request-local cleanup, CPU affinity, and reforking, and Puma's Fiber-per-request mode are disabled. Both threaded servers allow 999 requests per keep-alive connection.

CPU includes the server master and descendants, including SSE event production, but excludes client CPU and warmup. CPU ms/req divides that CPU time by successful ordinary requests. Peak aggregate PSS is sampled every 0.5s, proportionally accounting for shared pages instead of counting them fully in every worker.

Development

After checking out the repo, run bin/setup to install dependencies. Then, run bundle exec rake to compile native extensions and run the tests. You can also run bin/console for an interactive prompt that will allow you to experiment.

On macOS (or any non-Linux host), bin/dev builds and drops you into a Docker image with Ruby and the required Linux toolchain preinstalled, mounting the repo at /workspace. Run bin/dev for an interactive shell, or bin/dev <command> for one-off commands like bin/dev bundle exec rake or bin/dev bin/benchmark.
